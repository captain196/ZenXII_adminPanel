## 15. Sibling Import — **P14-1, the phase's most important finding [N]**

**Phase 13's fix is correct for a first import.** Two siblings sharing a parent phone but having
different names are both created; the same student re-imported is still deduped; case and whitespace
are normalised. That much is verified by test.

**But it is NOT idempotent on re-import.** Walkthrough of the current code:

```
Import #1 (Rahul, Priya — both phone 9999999999):
   Rahul created  → indexPhones[999…] = Rahul
   Priya created  → indexPhones[999…] = Priya      ← OVERWRITES (set(), merge=false)

Import #2, same file, skip policy:
   Row Rahul → in-file map empty at start
             → _existingStudentIdByPhone(999…) → PRIYA's id
             → _studentNameMatches(Priya, "rahul sharma") → FALSE
             → NOT a duplicate → ★ SECOND RAHUL CREATED ★
   Row Priya → resolves to Priya, name matches → correctly skipped
```

**Root cause:** `indexPhones` is one-phone → one-studentId (`Sis.php:4957`, `set(..., merge=false)`).
A family cannot be represented in it. Phase 13 corrected the **dedup rule** but not the **index
shape** — and the index shape is precisely what the in-repo spec `ZENX_ADMISSION_DOMAIN_SPEC.md`
already prescribed changing ("`indexPhones` becomes append, not overwrite").

**Severity: HIGH** — creating duplicate student records is worse than skipping a row, and re-running
an import is a normal operator recovery action.

**Is it a regression?** Partly. Before Phase 13, re-import under `skip` created no duplicate (it
wrongly treated the sibling as a duplicate) but the **first** import already lost the sibling. So:
old = data loss on first import; new = duplicate on re-import. **The new failure is less destructive
but must still be closed.**

**Recommended fix (NOT implemented, needs authorization):** make `indexPhones` hold a *set* of
studentIds per phone (append, not overwrite), and have `_existingStudentIdByPhone` return all
candidates so name corroboration can test each. Estimated: 1 file (`Sis.php`) + the same
`indexPhones` write in `enroll_student`/`save_admission`; **0 additional reads** (same single doc,
larger payload); no rules/index change. **Migration:** existing 1:1 documents read as a single-element
set — backward compatible, **no backfill required**.

**SRNO allocation for surviving siblings [F]:** correct. Both siblings pass dedup and reach the SRNO
block, which runs *after* it. In `new` mode each gets its own `allocateNext()` value; in `historical`
mode each must carry a distinct `SR Number` column value, and a collision is rejected with full
rollback rather than silently reassigned.

## 20. RTDB Audit — **P14-2 [N]**

**The student admission/import path still writes RTDB.**


`Common_model::addKey_pair_data()` (`models/Common_model.php:337-347`) calls
`$this->firebaseDatabase->getReference($parentNode)->update($data)` — **Realtime Database**.

**Why every previous sweep missed it:** all prior RTDB audits grepped `$this->firebase->get/set/push/
update/delete/shallow_get`. This is a different call shape (`$this->CM->…`), so the greps were
structurally incapable of finding it. **8 call sites total: `Staff.php` ×4, `Sis.php` ×3,
`Schools.php` ×1.**

**Impact:** it does not block SRNO (SRNO never touches these nodes) and does not corrupt Firestore.
It is a **standing violation of the Firestore-only line** in the student admission path, and it means
the phone index exists in *two* places with different shapes — relevant to P14-1's fix.

**Not touched.** Migration is a separate authorized workstream (§25-D4).
