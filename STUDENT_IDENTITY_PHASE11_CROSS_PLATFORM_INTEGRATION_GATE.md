## 1. Executive Summary

The identity *architecture* is sound and the Admin Panel uses it correctly. The gate does **not**
pass cleanly, however — this audit found **three real defects and two genuine integration gaps**,
two of which are live user-visible bugs that exist *today*, independent of anything Phase 11 would
add.

**The headline answer to the phase's core question:** yes, both mobile apps can display SRNO and
Admission Number at **ZERO additional Firestore reads**. In both apps the student document is
*already fully downloaded* — the fields are on the wire right now and silently discarded because
the Kotlin models don't declare them. The work is declaration-plus-UI, not a new query.

**But two defects must be fixed first or alongside**, because they are already producing wrong
output to real users:

- **P11-D1 (HIGH, live now):** the Teacher App renders `Roll: -2147483648` for any student whose
  roll number is blank or non-numeric — and Phase 9.2 *deliberately made the Admin Panel accept
  alphanumeric roll numbers*, so the panel now actively creates the data that breaks this screen.
- **P11-D2 (MEDIUM, live now):** the Parent App shows a **hardcoded** `#4` as every child's class
  Rank, to every parent in every school.

**Verdict: READY WITH CONDITIONS** (§20).

## 5. Parent App Audit (FRESHLY VERIFIED)

**Canonical screen:** `ui/profile/ProfileScreen.kt`. Its expanded "Student Detail Card"
(`:317-349`) already renders **Student ID** = `user.userId` (`:324`), alongside DOB, Gender,
Admission Date, contact, family, school, session.

**Critical architectural fact:** the Profile screen does **not** read `StudentDoc` at all. It reads
the DataStore-cached `User` object (`ProfileViewModel.kt:194-200` → `StudentRepository.kt:46` →
`TokenManager.kt:66-89`). `StudentFirestoreRepository` isn't even injected into `ProfileViewModel`.

**But the fields are already downloaded.** `AuthRepository.loadProfileFromFirestore()`
(`AuthRepository.kt:178-231`) performs a **full-document GET** of `students/{schoolId}_{userId}`
(`:186-188`). The wire payload already contains `srNo`, `admissionNumber`, `Admission Number`,
`apaarId`, `previousStudentId` — all discarded because `StudentDoc.kt:35-104` declares no matching
properties. Two other existing full-doc reads (`SplashViewModel.kt:108` every cold start;
`DashboardViewModel.kt:328` every dashboard load) would equally supply them.

**⇒ Displaying SRNO + Admission Number costs ZERO additional Firestore reads.** The change is a
declaration chain: `StudentDoc` → `User` → `TokenManager` DataStore keys → `ProfileDetailRow`.

**Reusable UI:** `ProfileDetailRow(label, value)` at `ProfileScreen.kt:1053-1074` (renders nothing
when blank — so a student without an Admission Number degrades silently, no empty row).

**Cache safety:** DataStore reads are key-by-key with `?: ""` defaults (`TokenManager.kt:66-89`) —
adding keys cannot break existing installs; they show blank until the next login/splash/dashboard
write, which self-heals on the very next cold start.

**Sibling switcher caveat (NEW FINDING, P11-G3):** `DashboardViewModel.switchToSibling()`
(`:248-318`) *rebuilds* the `User` from a fresh `getStudent()` and lists fields explicitly
(`:260-274`). Any new identity field must be added **there too**, or a parent who switches to a
second child would see the first child's SRNO blank out. Easy to miss.

## 6. Teacher App Audit (FRESHLY VERIFIED)

**Roster:** `ui/students/StudentsScreen.kt` → `StudentCard` (`:413-527`) shows photo, name,
`"Roll: {rollNo}"` (`:470-475`), father's name, flag + call buttons.

**Student detail:** there is **no separate navigable route** — `NavGraph.kt:170/:608` declares only
`Route.Students`. Detail is an in-screen side panel, `StudentDetailPanel` (`:529-636`), which
**already shows Student ID** via `ProfileDetailRow` (`:613-621`), plus father/mother/DOB/gender/
phone/email/address/admission date and a fee snapshot.

**Zero-read confirmation:** both roster paths call `queryDocumentsAs<StudentDoc>`
(`StudentFirestoreRepository.kt:59`, `StudentRepository.kt:74`), and `FirestoreService.kt:60-66`
does a plain `.get()` with `whereEqualTo` filters only — **no `.select()`/projection exists anywhere
in the file.** The full document is already downloaded. Adding `srNo` to `StudentDoc.kt` populates
it with **zero extra reads**.

**Reusable UI:** `ProfileDetailRow(label, value)` at `StudentsScreen.kt:720-744` — the exact
composable already rendering the nine detail rows.

**⚠ `@PropertyName` hazard (NEW FINDING, P11-R1):** the space-containing key `Admission Number`
cannot be a Kotlin property name and would need `@PropertyName`. The Teacher `StudentDoc` docblock
(`:20-23`) explicitly records that a `@PropertyName` alias colliding case-insensitively with an
existing property **crashes the whole document**. **Mitigation: use only the camelCase
`admissionNumber` field** — which the Admin Panel already dual-emits precisely for this reason.
Do not bind the spaced variant in either app.

## 7. Re-admission Cross-Platform Trace

Scenario: `STU0001`/SRNO 12/`2026/7K4P92` → re-admitted as `STU0047`/SRNO 12/**new** Adm No.

| Platform | Shows current Student ID? | Preserved SRNO? | Current Adm No? | Loses/duplicates child? |
|---|---|---|---|---|
| Admin Panel | ✔ `STU0047` | ✔ 12 | ✔ new | No — old record intact, linked via `previousStudentId` |
| Parent App | ✔ — parent re-logs in against the new Student ID; `User.userId` is rebuilt from Auth claims + the new doc | ✔ (once fields added) | ✔ (once added) | No duplication: the sibling matcher keys on phone+parent-name, and the old record is Withdrawn/Inactive so it is excluded from active queries |
| Teacher App | ✔ roster queries `status == "Active"` (`StudentFirestoreRepository.kt:62-65`), so only the new record appears | ✔ (once added) | n/a (§8) | No — old record filtered out by status |

**Historical vs current distinction:** neither app displays `previousStudentId`, and **neither
should** — a parent seeing a second "old" ID would be confusing, and a teacher has no workflow for
it. Historical linkage belongs in Admin Panel / Student 360 only. **Recommendation: do NOT surface
`previousStudentId` in either app.**

## 8. Should the Teacher App show Admission Number? — **NO. Documented decision.**

A teacher's workflows are attendance, marks, homework, flags, PTM. None of these reference an
admission-event identifier; the identifiers a teacher actually needs are **Roll Number** (classroom
operations) and **Student ID** (already shown, for support/escalation). SRNO is worth adding — it is
the number the school office and printed registers use, so a teacher fielding a parent query can
match it. Admission Number is an office/certificate artefact with **no teacher-facing workflow**.

**Decision: SRNO yes (detail panel), Admission Number no.** Adding it "for completeness" would add
clutter to the one detail surface teachers use, against Part 5's explicit instruction.

# 21. Plain-Language Summary

**The good news.** Everything about *how* students are identified is correct. Student ID is global,
SRNO restarts at 1 per school, Roll Number stays with the class, and the new Admission Number is
random and independent. Nothing in the whole system looks up a student by SRNO or Roll Number —
everything uses Student ID — which is exactly why promotion and re-admission can't break anything.

**The best news.** Showing SRNO and Admission Number in both apps is **free**. Both apps already
download the complete student record from Firestore; they just throw these fields away because
nobody told the Kotlin code they exist. We add a few lines declaring the fields and a few lines
showing them. **No new database queries, no slower screens.** Given how slow Firestore has been for
you, that matters.

**The bad news — two things are broken right now, for real users.**

1. **The Teacher App shows `Roll: -2147483648`.** If a student's roll number is empty (which is
   common — it's optional everywhere) or has letters in it, the app tries to turn it into a number,
   fails, and displays a giant negative number. It's on both the class list and the detail panel.
   The attendance screen already guards against this — so someone knew about the problem and this
   screen was simply missed. **And we made it worse:** in Phase 9.2 we deliberately allowed
   alphanumeric roll numbers in bulk import, so the Admin Panel now creates exactly the data that
   breaks this screen.

2. **The Parent App tells every parent their child ranks `#4` in class.** It's not a calculation —
   it's the literal text `"#4"` written into the code. Every parent, every school, every child. You
   need to decide: delete it, or build a real ranking.

**Three smaller things.** A withdrawn student's status resets to "Active" whenever the parent app
restarts. Hard-deleting a student leaves the Admission Number and APAAR index entries pointing at a
student who no longer exists (SRNO handles this correctly, the other two were missed). And the
Admin student list, import results screen, and printed credentials PDF still don't show SRNO or
Admission Number, even though every other screen does.

**One thing to watch.** When we import a school's *historical* students, the Admission Number gets
the *current* year, not the year they actually joined. It's harmless while only staff can see it —
but the moment we show it in the Parent App, parents will see a wrong year. Worth deciding now.

**My recommendation:** fix the two live bugs first, then do the mobile display work, then Fees.
